### AP14. `tooling` — C22: a fresh-user first-success gate

**Root cause:** the install → init → install-generators → generate →
typecheck path has no automated exercise from a clean machine against
public jsr.io. Three blockers and one broken stock generator lived on
it simultaneously, all found by one manual session.

**Evidence:** docs-journey#6 (age gate), #7 (fleet pin skew → 23
zero-byte files, every result `success`), #8 (stock mutation hooks
don't typecheck), format-agnostic#3 (flagless `deno install` yields a
`skmtc` that exits 70 on every generate) — 4 defects, 1 session.

**What to do:** add a scheduled (nightly or on-release) GitHub
Actions job — new workflow `.github/workflows/first-success.yml`,
`runs-on: ubuntu-latest`, no repo checkout of built artifacts — that:

1. installs the CLI the way the docs tell users to
   (`curl -fsSL https://skm.tc/install | sh`), on the **latest stable
   deno**, against **public jsr.io** (`JSR_URL` unset);
2. runs tutorial 01 verbatim: `skmtc init`, `skmtc install
   @skmtc/gen-typescript @skmtc/gen-zod
   @skmtc/gen-tanstack-query-fetch-zod`, `skmtc generate` against the
   Petstore spec committed as the fixture;
3. asserts **non-empty output**: every path in the manifest has
   `characters > 0`, and the file count matches a pinned floor;
4. runs `deno check` over the generated tree (this is what would have
   caught docs-journey#8 before publish);
5. fails loudly with the manifest attached as an artifact.

**Success criterion:** a fleet pin skew, an age-gate regression, a
missing shim flag, or a stock generator emitting uncompilable code
fails this job within 24 hours of publish, rather than being found by
the next person who reads the tutorial.

**Verification:** deliberately republish one stock generator pinned to
a stale core in a scratch scope and confirm the job goes red on step
3; then check the next 3 retro files for zero "fresh install produced
nothing/broken" entries.

### AP16. `skmtc-code` — C24: assert the impossible states at the render boundary

**Root cause:** see C24. Three distinct silent-output defects in one
period, each individually cheap to detect at the point where the
engine already has the evidence in hand.

**Evidence:** docs-journey#7 (empty file map + all-success),
kotlin-sdk#4 (33 files dropped when `removeErroredItems` pruned a
per-resource aggregate its non-errored siblings still expected),
addendum's controller#3 residue-file singleton (now a second instance
of "errored items leave partial artifacts").

**What to do:**

1. `core/context/RenderContext` — when the rendered artifact map is
   empty (or every file is zero-length) while `results` contains at
   least one `success`, emit an error-level diagnostic naming the
   condition; this state is unreachable in a correct run and is the
   exact signature of the dual-copy hazard.
2. `removeErroredItems` — when pruning a Definition that other
   non-errored items reference, record a distinct manifest entry
   (`PRUNED_REFERENCED_DEFINITION`) and print it on stderr. Silent
   pruning of a shared aggregate is indistinguishable from "the
   generator never made it."
3. Discard files whose only content is registered imports when the
   producing item errored (the residue-file case), or mark them in the
   manifest so on-disk evidence stops contradicting it.

**Success criterion:** re-running the docs-journey#7 pin skew produces
a loud failure instead of 23 zero-byte "successes"; a generator whose
first member operation errors loses the member, not the aggregate — or
is told, on stderr, that it lost the aggregate.

**Verification:** next 3 retros contain no entry whose surprise is
"generation reported success but the output was empty/missing."

### AP19. `skill-update` — C25: freshness discipline in the verify-first stance

**Root cause:** two independent verifications in one period passed
against stale state. The skmtc-debug skill's verify-first stance says
*reproduce before proposing*; it does not say *prove your observation
is of the new bytes*.

**Evidence:** csharp#3 (stale bound server → one wasted immutable
release), format-agnostic#4 (pipeline masked generate's exit code →
validated the previous run's artifacts).

**What to do:** add to `docs/skills/skmtc-debug/SKILL.md`'s verify-first
section, as three concrete rules:

1. **Take the exit code from the command under test**, never from a
   pipeline tail — `skmtc generate … | tail -2 && verify` reports
   `tail`'s status. Capture output to a file, or check
   `PIPESTATUS`/`set -o pipefail`.
2. **Assert freshness before validating content.** SKMTC's
   write-products persist across runs by design, so a failed generate
   leaves a fully plausible, self-consistent previous state on disk.
   Check the manifest's mtime moved, or plant a nonce.
3. **Kill by port, not by name, before every live gate**
   (`lsof -ti :PORT | xargs -r kill`), and assert the new process
   printed its listening line before issuing the first request — a
   backgrounded server that fails to bind is silent from the harness's
   view and the gate then measures the previous build.

**Success criterion:** no future entry describes a verification that
passed against prior state.

**Verification:** next 3 retros — grep for "stale", "previous run",
"already running".
