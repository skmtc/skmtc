### AP1. `tooling` — C11: silent wrong-artifact resolution (escalated recurrence of C3)

**Root cause:** four distinct Deno resolution mechanisms each silently
select a different artifact than the one the user believes is under
test: (a) a `jsr:@skmtc/gen-x@<v>` import resolves to the local
workspace member only on exact version match, else falls back to JSR
with no warning (2026-05-21-generators-core-upgrade#1/K5 — 56 type
errors masked mid-migration); (b) a member's own `deno.json` pin
shadows a root import-map mapping (2026-06-11#1 — Kotlin e2e gate ran
against published 0.1.0 instead of local 0.2.0); (c) `deno.lock`'s
workspace section retains stale resolution after pin bumps
(2026-05-27#1); (d) breaking core changes ship as silent runtime
failures because `deno bundle` is type-blind (2026-05-27#6,
`ModelDriver` variant requirement).

**Evidence:** 2026-05-21-generators-core-upgrade#1, 2026-05-27#1,
2026-05-27#6, 2026-06-11#1 (4 instances, 3 sessions; prior-period C3
evidence carries the family).

**What to do:**
1. Add to `cli/lib/doctor-headless.ts`:
   `lock-resolution-matches-pins/<project>` (compare `deno.lock`
   workspace-section resolution against `deno.json#imports` pins) and
   `workspace-pin-alignment` (flag any `jsr:@skmtc/*@<v>` import whose
   `<v>` mismatches a same-name local workspace member's version —
   the silent-fallback case).
2. Add an opt-in `deno check` of generator source to the bundle flow
   (`skmtc bundle --check`), so type-visible breaking changes (the
   0.6.7 `variant` requirement) surface at bundle time instead of first
   `transform` call.
3. `doc-update` rider: record the two resolution-precedence gotchas
   (member-pin-shadows-root and exact-version-or-JSR-fallback — they
   are inverse directions of one rule) together in
   `skmtc-generators` CLAUDE.md and the generator skill, plus a core
   0.6→0.9 migration note covering the `variant` requirement
   (2026-05-21-generators-core-upgrade#2's ask).

**Success criterion:** `skmtc doctor` flags a stale lock or a
version-mismatched workspace pin before any test/e2e is run; next 3
retro files contain zero "ran against a different version than I
believed" entries.

**Verification:** grep next 3 retros for `shadow`, `stale`, `pinned`,
`wrong version` — any wrong-artifact instance means the checks missed a
resolution mechanism.

### AP2. `tooling` + `skmtc-code` — C10: clone output & imported-vs-cloned exclusivity

**Root cause:** `skmtc clone` writes fully-versioned `jsr:` URLs into
cloned source (bypassing the import map; an 82-file rewrite per core
bump) and pins peer generators to JSR even when sibling clones sit in
the same project (edit→republish→repin cycle instead of edit→rebundle).
Separately, nothing enforces that a generator is *either* imported
*or* cloned: when both a `jsr:` import and an on-disk `gen-X/` folder
exist, the workspace resolver silently picks the folder. The invariant
and its check were fully designed in 2026-05-28-composition#3 and
implemented hub-side (`checkCompositionConsistency`, 422 on
inconsistent upload); the CLI half is unbuilt.

**Evidence:** 2026-05-24-clone-peer-references#2, #3,
2026-05-28-composition-consistency#3, 2026-05-24-gen-tanstack K5
(4 instances, 3 sessions).

**What to do:**
1. `skmtc-code` — `clone` writes bare specifiers in source (matching
   canonical `skmtc-generators/` style) and, when a referenced peer
   exists as a sibling clone, maps it to `../gen-x/mod.ts` in the
   clone's `deno.json` instead of a JSR pin.
2. `tooling` — port `checkCompositionConsistency` to a
   `composition-consistency/<project>` doctor check (jsr-import ⇒ no
   same-name folder; local-path import ⇒ folder must exist; every
   `gen-*/` folder referenced exactly once).
3. `skmtc-code` — `install` refuses (without `--force`) when
   `./gen-X/` exists; `clone` no-ops/refreshes when the import is
   already local.

**Success criterion:** a fresh clone of a generator with cloned-peer
siblings is editable and rebundlable with zero manual `deno.json` or
source edits; doctor flags a jsr-import+folder coexistence; next 3
retros contain zero clone-rewrite or both-states entries.

**Verification:** next 3 retro files — no entry describing hand-editing
cloned source imports or a silently-vendored generator.

### AP3. `skmtc-code` — C13 + C12: stock tanstack template blockers and the `--json` contract

**Root cause (C13):** `gen-tanstack-query-fetch-zod` stock templates
fail consumer typecheck/runtime three ways: destructured path params

operation); `MutationFn` emits a zero-param arrow referencing bare

signature. The session's `win` entry (#4) already names the durable
fix: the `args.*` emission pattern via `toPathTemplate(path, 'args')`
eliminates the entire shadowing class. **Root cause (C12):** `--json`
mode emits unparseable stdout exactly when agents need it — the
`parseIssue.parent` field is string-concatenated unescaped (invalid
JSON document), and ANSI `[WARN]` logs interleave on stdout despite the
skill documenting logs-on-stderr.

**Evidence:** C13: 2026-05-24-gen-tanstack-query-integration#1
(blocker), #2 (blocker), #3; C12: 2026-05-28-large-schema-profiling#2,
2026-05-31-reapit#7 — 2 sessions each.

**What to do:**
1. Rewrite the stock templates on the `args.*` pattern; destructure
   `variables` in `MutationFn`; emit the v5 4-arg `onSuccess`. Verify
   by `skmtc generate --typecheck` against a consumer fixture with the
   real deps installed.
2. `JSON.stringify` the `parseIssue.parent` value at the serialization
   site; route all `[WARN]` parse-issue logs to stderr in `--json`
   mode; add a test asserting `JSON.parse(stdout)` succeeds on a
   schema that produces parse issues.
3. `skill-update` rider — promote `--typecheck` in `skmtc-cli` SKILL
   §10 as the default verification step, with the precondition from
   2026-05-21-typecheck-external#1: it measures generator quality only

**Success criterion:** stock tanstack output typechecks clean against a

**Verification:** grep next 3 retros for `shadow`, `body is not

### AP4. `skmtc-code` — C14: emission helpers that silently emit wrong output

**Root cause:** three core surfaces compile fine and emit broken or
wrong code at edges the type system can't see:
`FunctionParameter`/`toDestructured` render non-identifier keys
(`If-Match`, `user-id`) unquoted — invalid JS in a binding pattern, and
`FunctionParameter.test.ts` asserts the broken output;
`TsObject` derives `?` from `value.modifiers.required`, so
`addProperty({ schema: new CustomValue(...), required: false })` is a
silent no-op (always required); `GeneratorConfig.transform`'s generic
`<Acc>` variance rejects every monomorphic factory-emitted transform,
institutionalizing `// @ts-expect-error` on every entry.

**Evidence:** 2026-05-31-reapit#1, #2,
2026-05-21-generators-core-upgrade#3 (3 instances, 2 sessions).

**What to do:** in `@skmtc/core`: apply `handleKey` quoting inside
`toDestructured`/`FunctionParameter` for non-identifier keys and fix
the test to assert the quoted form; make `CustomValue` accept/carry
`modifiers` (or have `TsObject` honor the `addProperty` `required` flag
when the value has none — pick one, document it); revisit
`GeneratorConfig.transform`'s `<Acc>` so a `=> void` transform is
assignable without suppression.

**Success criterion:** a header-named param destructures to valid JS;
`required: false` on a `CustomValue` prop emits `?`; zero
`@ts-expect-error` needed on factory entries; next 3 retros report no
silently-wrong helper output.

**Verification:** next 3 retros + grep `skmtc-generators` for the
`@ts-expect-error - factory-emitted` comment (should be deletable).

### AP7. `skmtc-code` — C16: attribution pointer faithfulness

**Root cause:** three independent faithfulness gaps in the

origin; (c) render-tree child capture has a hidden precondition —
gen-typescript's inner snippets appear, gen-zod's structurally
identical ones silently don't.

**Evidence:** 2026-05-31-attribution-systematic-design#1, #2, #4, #5,
#6 (1 session, 5 entries, live-verified on core 0.6.10).

**What to do:** (decision A/B/C on trail separation is pending with
the user — resolve that first.) Separate document position from
operational trace on `StackTrail` (two trails, or a documented strip
rule in `attribute.ts:43`); preserve member origin through the allOf
merge (`toSchemasV3.ts:84-92`) for non-overlapping fields; debug
gen-zod's render path until `ZodObject`/`ZodString` edges appear, then
document the capture precondition as a caveat on the transparent-
capture claim. Also mark `worker.ts` + `deno.json#workspace` as the
authoritative "what runs" sources in the architecture skill (#6).

**Success criterion:** a granular pointer from a threaded snippet

documented, union collapse is not). Review follow-up (2026-06-11)
established that the collapse itself is correct, not a defect:
single-member `oneOf` is overwhelmingly the OAS 3.0 workaround for
`$ref` not permitting sibling annotations; the parse distributes the
wrapper's siblings (`description`, `nullable`, `x-*`) into the member
before collapsing (`decomposeUnion` → `mergeCrossProduct` →
`toSchemasV3.ts:113`; only `discriminator` and `default` are dropped,
both degenerate on a one-member union); and openapi-generator's
default-on `SIMPLIFY_ONEOF_ANYOF` normalizer performs the same
collapse. Collapse-to-annotated-member is intended and
ecosystem-standard — the gap is documentation only, no parse change
warranted. Adjacent gap, same audience: the
factory-entry wrapper recipe (import-map key → local wrapper `mod.ts`
default-exporting `toXEntry({...})`, factory imported via full `jsr:`
specifier) failed twice before landing and will recur with
gen-kotlin-spring (2026-06-11#3/K3).

**Evidence:** 2026-06-11-kotlin-sealed-oneof-spring#2, #3 (1 session,
but the Spring milestone — next on the roadmap — hits both

**Probe result (2026-06-11, scratch through the real convert→parse
path):** SKMTC consumes OAS 3.1 only via 3.1→3.0 down-convert.
`openapi-down-convert/converter.ts:315` folds the type-array form

intent was lost end-to-end with zero diagnostics.
