### AP1-amendment. `tooling` + `skmtc-code` — C19: resolved-module-graph uniqueness (dual-copy)

**Root cause:** see C19. The prior AP1 targeted *wrong single version*
(pin/lock skew); these two entries show the sibling failure — *two
versions simultaneously* — needs its own check, because `deno.json`
pins can all look individually correct while the resolved graph holds
two copies (local-path wrapper + jsr pin of a dependent generator is
the canonical trap).

**Evidence:** 2026-06-11-spring-server-execution#1,
2026-06-11-controller-service-union-hints#2 (2 sessions, 2 mechanisms).

**What to do:**
1. `tooling` — extend AP1's doctor work with
   `single-copy-per-package/<project>`: after resolution (or at
   bundle time, where the module graph is in hand), assert exactly one
   resolved version per `@skmtc/lang-*` and `@skmtc/gen-*` package;
   error names both versions and the import chains that pulled them.
2. `skmtc-code` — replace `instanceof` guards in lang render paths
   with duck-typed discriminants (`importEntry.langId === 'kotlin' &&
   importEntry.kind === 'import'` style), starting with
   `KtFile.toString()`'s `KtImport` check and `isKtAnnotated` /
   `isKtConstructed` / `isKtSupertyped`; audit `lang-typescript` and
   core's `SnippetBase`/`DefinitionBase` checks for the same exposure.
3. `doc-update` rider — add the **all-local-or-all-jsr wrapper rule**
   to the skmtc-cli skill's local-generator task card: during
   pre-release validation, point ALL wrappers at local sources, not
   just the changed one; one mixed pin re-introduces the split.

**Success criterion:** a project mixing a local gen-kotlin with a jsr
gen-kotlin-spring fails loudly at doctor/bundle time naming both
copies; lang render behavior is `instanceof`-free so a residual dual
copy degrades to correct-but-redundant imports instead of silent
drift; next 3 retros contain zero dual-copy entries.

**Verification:** grep next 3 retros for `instanceof`, `two copies`,
`basePackage is not set`, `dual`.
