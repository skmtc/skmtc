### P1. `skmtc-code` — C1: `skmtc bundle` false-failure

**Root cause:** `@skmtc/cli@0.3.4` threads `bundlePath` as a `file://`
URL *string* (from `toBundlePath`). `bundleHeadless`'s post-write
existence check passes that string to `@std/fs`'s `exists`, which (like
Deno's fs APIs) resolves a `file://` scheme only from a `URL` *object*
— a `file://` *string* is treated as a literal, non-existent path. The
check therefore false-negatives 100% of the time for any
local-generator project, throwing `bundle.js was expected at <path>
but wasn't written` *after the bundle has already been written
successfully*. Confirmed in `2026-05-21-cli-bundle-deno-version.md` K5
and entry #4.

**Evidence:** `2026-05-13-shadcn-form-allow-list#1`,
`2026-05-15-bodywrapper-hidden-prop#1`,
`2026-05-15-wizard-standalone-cleanup#1`,
`2026-05-16-table-generator-poc#1`, `2026-05-17-cross-gen-composition#6`,
`2026-05-18-shadcn-form-job-site-variant#1`,
`2026-05-20-clone-generator-version-skew#6`,
`2026-05-21-cli-bundle-deno-version#4` — 8 instances, 8 distinct
sessions, 3 tagged `blocker`.

**What to do:** In `cli/lib/bundle-headless.ts` (the check at ~line 70),
either (a) convert the `file://` URL string to a filesystem path with
`fromFileUrl()` before calling `exists`, or (b) construct a `URL`
object and pass that. Audit every other consumer of `toBundlePath`'s
return value for the same string-vs-URL confusion. Add a regression
test that runs `bundleHeadless` against a real local-generator project
and asserts exit 0.

**Success criterion:** `skmtc bundle <project>` exits 0 for a
local-generator project whose `bundle.js` was written; the next 3 retro
files contain **zero** new "bundle.js wasn't written" entries.

**Verification:** grep the next 3 retro files for `wasn't written` /
`bundleHeadless` — any hit means the fix missed or regressed.

### P2. `skmtc-code` — C2: bundle/clone failures are opaque

**Root cause:** `createBundle` (`cli/tasks/GenerateBundleTask.tsx:95`)
runs `deno bundle` with stdout/stderr piped to
`<project>/.settings/logs.txt` and `.settings/error-logs.txt`, then on
failure throws a bare `new Error('Failed to create bundle')`. The
captured stderr — the only diagnosable cause — is in neither the thrown
error nor the strict-mode `--json` result. Every distinct failure
(wrong Deno version, missing export, bad specifier) collapses to the
same opaque message.

**Evidence:** `2026-05-20-clone-generator-version-skew#2`,
`2026-05-21-cli-bundle-deno-version#1`,
`2026-05-21-cli-bundle-deno-version#2` (the Deno-≥2.4 requirement was
undiagnosable *because of* this opacity).

**What to do:** In `createBundle`, on `!success`, read back the
captured `error-logs.txt` content and include it in the thrown
`Error` message and in the strict-mode JSON `detail` field. At minimum,
name `.settings/error-logs.txt` in the error output. Ships in the same
PR as P1 (same code area).

**Success criterion:** a `skmtc bundle` / `skmtc clone` failure surfaces
the underlying `deno bundle` stderr (or names the log file) in its own
output; retros stop reporting "had to read the CLI source to discover
`error-logs.txt` existed."

**Verification:** next 2 retro files — no entry describing a bundle
failure diagnosed only by reading CLI source or undocumented log files.

### P3. `tooling` + `skmtc-code` — C3: fresh-project dependency closure is unvalidated

**Root cause:** no command or check guarantees a project's dependency
closure (CLI / core / worker / generators / Deno runtime) is internally
consistent and bundlable. `skmtc clone` writes a `deno.json` with only
`@skmtc/gen-*` local mappings + `workspace[]` — omitting the
`@skmtc/worker` pin that the CLI-generated `worker.ts` imports, so
`deno bundle` fails `Import "@skmtc/worker" not a dependency`. Cloned
stock-generator source imports core via fully-versioned specifiers
(`jsr:@skmtc/core@0.5.1`), not the import map. `install` of "latest"
across several generators yields a non-co-released, core-skewed set.
`@skmtc/cli@0.3.4` silently requires Deno ≥ 2.4 (for `deno bundle -o`).

**Evidence:** `2026-05-20-clone-generator-version-skew#3` (blocker),
`#4`, `#5`; `2026-05-13-shadcn-form-allow-list#2` (blocker), `#3`;
`2026-05-21-cli-bundle-deno-version#2`. Knowledge rows: version-skew
K2–K5, cli-bundle K1.

**What to do:**
1. `skmtc-code` — `clone` and `init` must write a complete import map:
   add `@skmtc/worker` and `@skmtc/core` pins (matching the CLI's
   major.minor) to the project `deno.json` whenever a `worker.ts` will
   be generated.
2. `tooling` — add `doctor` checks: `project-worker-pin/<project>`
   (worker pin present and resolvable), `deno-version-floor` (running
   Deno ≥ the CLI's required minimum), and
   `project-generator-coversion/<project>` (all installed generators
   pin a mutually compatible `@skmtc/core`).

**Success criterion:** `skmtc init … && skmtc clone …` (or `install`)
followed by `skmtc bundle` succeeds with **no manual `deno.json`
edits**; `skmtc doctor` flags a missing `@skmtc/worker` pin and a
sub-2.4 Deno before `bundle` is ever run.

**Verification:** next 2–3 retro files — no entry describing a
hand-edited `deno.json` to make a cloned/inited project bundle.

### P4. `skmtc-core-feature` + `tooling` — C4: skip/include is not cross-generator-dependency-aware

**Root cause:** the skip/include filter is evaluated *before*
`transform`, independent of cross-generator dependency edges. When an
active generator B references generator A's output and A is skipped,
the result depends on *how* B references it: `insertOperation(A, op)`
materialises A's Definition regardless of A's skip config (and also
bypasses A's `isSupported`); a hand-replicated naming + string-import
path respects A's skip and emits a **dangling import** that fails only
at consumer typecheck. The behaviour is inconsistent and undetected.

**Evidence:** `2026-05-16-selector-generator-poc#1`,
`2026-05-17-cross-gen-composition#2`. Knowledge rows: table-poc K5,
selector-poc K4, cross-gen K2.

**What to do:**
1. `tooling` (cheaper interim) — add a `doctor` check
   `dangling-imports/<project>` and a generate-time manifest warning:
   compare every emitted import path against `manifest.files`; flag any
   import that resolves to no generated artifact. This surfaces the
   failure at generation time instead of consumer typecheck.
2. `skmtc-core-feature` (durable) — make the filter dependency-aware:
   a skipped generator referenced as a cross-gen dependency by an
   active generator is materialised (skip treated as advisory for
   dependency edges), while still respecting `isSupported`. The user
   articulated this exact principle in `2026-05-17-cross-gen#2`.

**Success criterion:** a skipped peer referenced by an active generator
either emits or produces a loud `dangling-imports` warning; retros stop
reporting "had to remove the endpoint from BOTH skip lists" and
"dangling import discovered at consumer typecheck."

**Verification:** next 3 retro files — no dangling-import-at-typecheck
entry; no paired-skip-edit entry.

### P5. `skill-update` + `skmtc-code` — C5: Projection/Driver constructor foot-guns

**Root cause:** the Projection/Driver contract has latent foot-guns the
type system does not catch: (a) constructor side-effects (`register`,
`insertNormalizedModel`, `insertOperation`) commit imports into the
destination File map *before* the Definition is registered — so a
defensive `invariant` placed *after* them leaves an orphan stub `.tsx`
(import header, no `export const`) when it throws; (b) a Projection can
declare a non-standard constructor arg shape that the type-checker
accepts but the Driver cannot satisfy; (c) `isSupported` static-override
typing traps when the base config didn't specify it.

**Evidence:** `2026-05-17-cross-gen-composition#1` (40 orphan stub
files), `2026-05-14-shadcn-form-refactor#2`,
`2026-05-13-promote-snippets-to-projections#3`, `#4`. Knowledge row:
cross-gen K5.

**What to do:**
1. `skill-update` — add to `deno/docs/skills/skmtc-generator/SKILL.md`
   §8 (Anti-patterns) a "Side-effecting calls before defensive
   invariants" entry, and to §9 (verification checklist) the line:
   *"Defensive invariants in a Projection constructor precede all
   side-effecting `register` / `insertNormalizedModel` /
   `insertOperation` calls, so a contract violation leaves no orphan
   file."* Add a §8 entry: *"A Projection's constructor args must equal
   `OasOperationProjectionConstructorArgs<E>`; needing more data means
   convert to a Snippet or read from `settings.enrichments` with an
   `invariant`."*
2. `skmtc-code` (robust complement) — make the Driver remove the File
   map entry when a Projection constructor throws, so a thrown invariant
   genuinely leaves no residue regardless of constructor ordering.

**Success criterion:** generator skill §9 contains the constructor-
ordering line; a constructor invariant throw produces no orphan `.tsx`;
retros stop reporting orphan-stub files.

**Verification:** next 3 retro files — no "orphan stub" / "import header
with no export const" entry.

### P6. `skill-update` → `skmtc-code` — C9: form-generator path-param coupling

**Root cause:** `gen-shadcn-form` emits
`useSafeParams(z.object({ <oasParamName>: z.string() }))` verbatim — a
**runtime** coupling, not just a naming convention: the consumer's
React Router param name must match the OAS path-param name or the form
throws a ZodError at mount. There is no alias seam and no loud
generation-time failure. Adjacent: `client.json` skip entries are
exact-match strings that silently become no-ops when an OAS path is
renamed.

**Evidence:** `2026-05-15-path-param-mismatch#1` (blocker — a
30-minute migration became a 14-file OAS rename), `#2`. Knowledge rows:
path-param K1, K3.

**What to do:**
1. `skill-update` — in `deno/docs/skills/skmtc-generator/SKILL.md` §7
   (customization seams), flag path-param naming as a *runtime*
   coupling, with a pre-migration check: *"before migrating a form,
   `rg ':<param>' src/router*` and confirm it matches the OAS
   path-param name — rename one side first."*
2. `skmtc-code` (durable) — add a `pathParamAlias: Record<string,
   string>` field to `gen-shadcn-form`'s enrichment schema so consumers
   can patch the mismatch without an API rename; and a `doctor`
   `skip-stale-entries` check that flags skip entries matching no
   current OAS path.

**Success criterion:** generator skill §7 names path-param naming as a
runtime coupling; retros stop reporting ZodError-at-mount from
param-name mismatch.

**Verification:** next 3 retro files — no path-param-mismatch entry.

### P7. `skill-update` + `example-addition` — C6: generator skill scaffolds mislead

**Root cause:** the `skmtc-generator` skill's scaffolds use *partial*
destructures (`isSupported({ operation, variant })`) that read as the
*complete* arg surface — `IsSupportedOasOperationConfigArgs<E>` actually
carries `context` and `enrichments` too. The "gating `isSupported` on
enrichment presence is an anti-pattern" rule has a real, unstated
carve-out (generators with no defaultable emission). There is no
end-to-end "author a new generator from scratch" recipe. Method-vs-
property foot-guns (`Inserted.toIdentifier()`) are under-covered, and
an LLM readily hallucinates a non-existent `ContentBase` base class.

**Evidence:** `2026-05-16-table-generator-audit#1`, `#2`,
`2026-05-13-static-toidentifier-rule#2`,
`2026-05-13-promote-snippets-to-projections#5`, `#6`,
`2026-05-16-table-generator-poc#3`. Knowledge rows: table-audit K1/K5,
table-poc K1/K4, tanstack K1, cross-gen K1, cli-bundle K4,
selector-poc K1.

**What to do:** In `deno/docs/skills/skmtc-generator/SKILL.md`:
- §6 scaffold C — destructure all four args (`context`, `operation`,
  `enrichments`, `variant`) with a comment noting which are usually
  unused, OR add an explicit "all four fields are available" note.
- §4/§8 — add the carve-out: *"the gate-on-enrichment anti-pattern
  assumes the generator has defaultable behaviour; a generator whose
  every emission requires a consumer-supplied non-defaultable pointer
  may legitimately short-circuit in `transform` (not `isSupported`)."*
- §8 — add an `Inserted.toIdentifier()` (method, not `.identifier`
  property) anti-pattern entry, sibling to the existing
  `OasRef.toRefName()` one.
- §10 — add a "Author a new generator from scratch" task card covering
  the 3-place workspace registration dance (table-poc K1).
- `example-addition` — a minimal model→file generator showing the exact
  `@skmtc/core` imports, hardening against the `ContentBase`
  hallucination; and fold in `2026-05-13-graphql#1`'s principle:
  *".generated.* output must be complete and working — never
  fill-in-the-blank stub content."*

**Success criterion:** retros stop reporting "I assumed `isSupported`
only gets `operation`/`variant`" and "scaffold misled me"; a from-
scratch generator card exists.

**Verification:** next 3 retro files — no scaffold-misled entry.

### P8. `doc-update` + `skmtc-code` — C7: multi-package output routing undocumented

**Root cause:** `client.json#settings.packages: [{ rootPath,
moduleName }]` and cross-package output resolution
(`normalizeModuleName`, `toResolvedArtifactPath`) are first-class in
`@skmtc/core` but appear in **no** skill or doc — discovered only by
reading core source. Sub-bug: writing artifacts outside `basePath`
requires hand-counting `..` segments off the depth of `basePath`; a
wrong count silently misplaces every artifact with no error, and
`packages[].rootPath` must track the same `..` prefix in lockstep.

**Evidence:** `2026-05-21-multi-package-output-routing#1`–`#6`.
Knowledge rows: multi-package K1–K5.

**What to do:**
1. `doc-update` — a `concepts/multi-package-output.md`; a `packages`
   section in `deno/docs/skills/skmtc-cli/SKILL.md` §6 (client.json
   shape); a settings-reference entry for `ModulePackage`. Document
   `register({ reExports })` and the "barrel = reExports-only File"
   pattern in the generator skill (lighter than the accumulator card).
2. `skmtc-code` — provide a basePath-relative / monorepo-root-anchored
   path helper, or make `toResolvedArtifactPath` fail loudly when an
   artifact resolves outside every declared package root, so a wrong
   `..` count cannot silently misplace files.

**Success criterion:** an agent working only from the skills can route
output into multiple monorepo packages; a wrong `..` count produces an
error, not silently-misplaced files.

**Verification:** next review — no entry reporting multi-package
support discovered by reading core source.
